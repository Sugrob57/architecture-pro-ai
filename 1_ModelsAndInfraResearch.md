# Архитектурный анализ и рекомендации по внедрению RAG-бота

QuantumForge Software

## 0. Ключевые вводные и ограничения

### Данные

Источники данных для LLM:
- Внутренние архитектурные решения (ADR), security-политики, SOC 2 материалы
- Клиентские PDF-спецификации (ABB, Wärtsilä)
- Рост базы: ~400 документов / месяц
- Документы живут в разных системах, но фактически:
    - GitHub / Confluence
    - PDF заказных проектов

### Риски и безопасность
- Наличие в компании ежегодного аудита (SOC 2) накладывает ограничения:
    - нужен контроль доступа
    - нужен аудит действий и общения с LLM
    - места хранения данных
- Часть контента нельзя безусловно отдавать в публичное облако LLM (например PDF-спецификации, ADR-решения)

### Требования для внедрения LLM

| N | Требование |
|---|------------|
| F1 | Система должна выполнять семантический поиск по корпаративной базе знаний и предоставлять выдержки из них по запросу |
| F2 | Система должна автоматически определять и предоставлять последнюю акутальную версию документов |
| F3 | Система должна предоставлять справочные данные согласно корпоративному глоссарию |
| F4 | Система должна предоставлять инструкции по настройке рабочего места и работе ИТ-систем компании |
| F5 | Система должна в явном виде фиксировать отсутствие документации по заданным вопросам |


### Вывод
Использование "только облачных" LLM не подойдет,  нужна гибридная RAG-архитектура.

## 1. Сравнение LLM-моделей

Локальные (Hugging Face) vs Облачные (OpenAI / YandexGPT)

### 1.1 Качество ответов
| Критерий	| Local LLM |	Cloud LLM |
|------|-------|----------|
| Общая когерентность |	Хорошая | Отличная |
| Работа с длинным контекстом | 8–32k (чем больше, тем дороже) | 32k (фиксированно) |
| Сложные why/how вопросы |	Средне | Отлично |
| Галлюцинации | Выше | Ниже |

Вывод:
- Для инженерных, архитектурных и compliance-вопросов Cloud LLM заметно лучше.
- Локальные LLM приемлемы только в RAG-режиме и с более конкретным промптингом.

### 1.2 Скорость работы
|Сценарий | Local LLM |	Cloud LLM |
|---------|---------------|--------------|
|Средний ответ | 1.5–4 сек | 0.8–2 сек |
|Параллелизм | Ограничен GPU | Нет ограничений |

### 1.3 Стоимость владения и использования

Local LLM:
- GPU A100 / L40S: $1 500–3 000 / мес
- DevOps + MLOps: ~0.3–0.5 FTE
- Электричество, простои, апгрейды

Вывод: $3000–6000 / мес

Cloud LLM:
- На примере (GPT-4o):
    - ~$5 / 1M input tokens
    - ~$15 / 1M output tokens

Вывод: При ~1000 запросов / день: $800–1500 / мес

### 1.4 Удобство и простота развёртывания

| Критерий | Local LLM | Cloud LLM |
|----------|-----------|-----------|
| Time-to-market | Недели | Дни |
| Поддержка | Своя | Vendor |
| Обновления моделей | Ручные | Авто |

### Вывод

- Cloud LLM — значительно проще
- Local LLM — обязателен для sensitive-данных

Рекомендуется гибрид:
- Публичные и внутренние документы => Cloud LLM
- Конфиденциальные и клинтские документы (в т.ч.PDF) => локальный LLM

## 2. Сравнение моделей эмбеддингов

### 2.1 Скорость создания индекса
| Критерий | Sentence-Transformers (local) | OpenAI Embeddings |
|----------|----------------------------------|-------------------|
| Индексация | Медленнее | Быстро |
| Масштаб | Ограничен CPU/GPU | Масштабируем |
| Batch-инг	| Ограничен	| Есть |

### 2.2 Качество поиска
| Тип запроса | Sentence-Transformers (local) | OpenAI Embeddings |
|---------------|----------|-----------|
| По ключевым словам |	Отлично | Отлично |
| Семантический | Хорошо-Отлично (в зависимости от качества обучения) | Отлично |
| Кросс-доменный | Хорошо | Отлично |

### 2.3 Стоимость

OpenAI embeddings:
- ~$0.02 / 1M tokens
- Все данные ≈ $20–40 разово

Sentence-Transformers (local):
- Бесплатно, но:
    - CPU
    - поддержка
    - latency

Итог по эмбеддингам
- OpenAI embeddings — лучший default
- Local embeddings — для изолированных сред / sensitive данных

## 3. Векторные базы: ChromaDB vs FAISS

### 3.1 Скорость поиска и индексации
| Критерий | ChromaDB |	FAISS |
|----------|----------|-------|
| Поиск	| Отлично | Отлично |
| Индексация | Отлично | Отлично |
| Производительность | Хорошая для большинства случаев, HNSW-индексация | Высокая, особенно с GPU (5-10x ускорение) |
| Количество векторов | Миллионы, горизонтальное масштабирование | Миллиарды |

### 3.2 Сложность внедрения и поддержки

| Критерий | ChromaDB | FAISS |
|----------|----------|-------|
| Персистентность | Встроенная | Ручная реализация |
| Метаданные | Полная поддержка фильтрации |Ограниченно |

### 3.3 Удобство использования
| Критерий	| ChromaDB | FAISS |
|-----------|----------|-------|
| API | Очень простой | Требует экспертизы |
| RAG-фреймворки | Нативно LangChain, LlamaIndex | LangChain, LlamaIndex - через обертки  |
| DevOps overhead | Низкий | Высокий |

### Вывод

ChromaDB — оптимальный выбор
- Быстро
- Просто
- Достаточно для 20–50k документов
- Отлично для MVP и production RAG
- проще в поддержке и использовании

FAISS имеет смысл только при:
- 10M+ документов

## 4. Рекомендуемая конфигурация сервера

### Вариант A — Все в облаке
- RAG-API (AWS EKS):
    - CPU: 4–8 vCPU
    - RAM: 16–32 GB
    - GPU: не требуется
    - Autoscaling
- LLM: OpenAI
- Embeddings: OpenAI
- Vector DB: ChromaDB (EBS)

### Вариант B — Hybrid
- Public RAG
    - OpenAI (LLM + embeddings)
    - ChromaDB
- Confidential RAG
    - GPU: L40S / A100
    - RAM: 64 GB
    - LLM: Llama / Qwen / Mixtral
    - Embeddings: Sentence-Transformers (local) 
    - Isolated VPC

## 5. Итоговые варианты архитектуры

### Вариант 1 — Cloud-only (MVP)
- Стоимость: Самый дешевый вариант ($800–1500 / мес)
- Риски: SOC 2 / NDA
- Кому подходит: PoC, demo

### Вариант 2 — Hybrid RAG (РЕКОМЕНДУЕТСЯ)
- Стоимость: Средне ($3000–6000 / мес)
- Безопасность: Да
- Масштабируемость: Да
- Гибкость: Да

### Вариант 3 — Fully On-prem
- Стоимость: Очень дорого (от $6000 / мес)
- Сложность: Высокая
- Когда нужно: Только если в облако нельзя ничего транслировать по требованиям регуляторов отрасли

### Вариант 4 — Product-ready RAG (SaaS)
- Стоимость: от $9000 / мес (все что было в предыдущих вариантах + мониторинг, поддержка, мультитенантность)
- ROI: Нужна экспертная оценка, но потенциально - высокий.
- Подходит для реализации "LLM как продукт для клиентов"

## 6. Финальная рекомендация

### Рекомендуемый стек

| Компонент | Выбор |
|-----------|-------|
| LLM | OpenAI + локальный LLM |
| Embeddings | OpenAI + local fallback |
| Vector DB | ChromaDB |
| Infra | AWS(EKS) |
| Security | Doc-level ACL + separate indexes |
| RAG-паттерны | Гибридный поиск + фильтрация по метаданным |

### Почему ChromaDB
- Минимальный time-to-market
- Отлично ложится на текущий AWS-стек
- Не требует отдельной команды поддержки
- Достаточна по производительности
- Поддерживает metadata => ACL => SOC 2
